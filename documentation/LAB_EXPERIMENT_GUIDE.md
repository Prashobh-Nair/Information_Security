## 3. Step-by-Step Procedure & Observations on Machine B

### Question 1 & 2: Source and Destination IP Addresses
- **During Ping Request**:
  - Source IP: `192.168.1.10` (Machine A)
  - Destination IP: `192.168.1.20` (Machine B)
- **During Ping Reply**:
  - Source IP: `192.168.1.20` (Machine B)
  - Destination IP: `192.168.1.10` (Machine A)

### Question 3: Network Layer Protocol Being Used
- **Protocol**: **IPv4 (Internet Protocol Version 4)**, EtherType `0x0800`.
- In the IPv4 header: `Protocol = 1` indicates **ICMP (Internet Control Message Protocol)**.

### Question 4 & 5: Source and Destination MAC Addresses
- **Echo Request Frame**:
  - Source MAC: `00:0c:29:1a:2b:3c` (Machine A's physical network adapter)
  - Destination MAC: `00:0c:29:4d:5e:6f` (Machine B's physical network adapter)
- **Echo Reply Frame**:
  - Source MAC: `00:0c:29:4d:5e:6f` (Machine B)
  - Destination MAC: `00:0c:29:1a:2b:3c` (Machine A)

### Question 6: ICMP Packet Type, Code, and Meaning
1. **Echo Request (Machine A → Machine B)**:
   - **Type**: `8`
   - **Code**: `0`
   - **Meaning**: `Echo Request`. A query probe sent by the source to verify destination host availability.
2. **Echo Reply (Machine B → Machine A)**:
   - **Type**: `0`
   - **Code**: `0`
   - **Meaning**: `Echo Reply`. Generated by Machine B in response to an Echo Request, returning identical payload data and identifier/sequence numbers.
3. **Common Diagnostic Types**:
   - `Type 3, Code 0`: Destination Network Unreachable
   - `Type 3, Code 1`: Destination Host Unreachable (ARP resolution failed)
   - `Type 3, Code 3`: Destination Port Unreachable (No service listening on destination port)
   - `Type 11, Code 0`: Time-to-Live (TTL) Exceeded in Transit (Traceroute mechanism)

## 4. Realization Across Traffic Types

### 1. ARP (Address Resolution Protocol)
- **EtherType**: `0x0806`
- **Request**: Opcode `1` (`Who has 192.168.1.20? Tell 192.168.1.10`), broadcasted to `ff:ff:ff:ff:ff:ff`.
- **Reply**: Opcode `2` (`192.168.1.20 is at 00:0c:29:4d:5e:6f`), sent unicast to Machine A.

### 2. DNS (Domain Name System)
- **Transport**: UDP Port `53`
- **Query**: Machine A queries for `portal.lab.lan` (Query Type `A`).
- **Answer**: Response returns IP address `192.168.1.20`.
- **Security Risk**: Cleartext transmission allows observers to map browsing activity.

### 3. HTTP (HyperText Transfer Protocol)
- **Transport**: TCP Port `80`
- **Security Risk**: **Zero encryption**. All HTTP methods (`GET`, `POST`), URLs, headers, and form bodies are completely visible in Wireshark.

### 4. HTTPS (HyperText Transfer Protocol Secure)
- **Transport**: TCP Port `443`
- **Handshake**: Negotiates TLS 1.3 with ECDHE key exchange.
- **Payload**: Marked as `Application Data (0x17 0x03 0x03)`.
- **Observation**: Passive sniffing cannot decrypt or read the request payload without private keys.

### 5. FTP (File Transfer Protocol)
- **Transport**: TCP Port `21`
- **Authentication**: Sends `USER lab_admin` and `PASS CleartextPassword` in cleartext over the LAN.

## 5. HTTP Password Sniffing Demonstration Walk-Through

1. Open NetSecure at `http://127.0.0.1:8000`.
2. Click **HTTP Password Sniffer** in the left sidebar.
3. Select **HTTP (Unencrypted)** mode.
4. Input credentials:
   - Username: `student_alex`
   - Password: `Secr3tLabP@ssw0rd!`
5. Click **Submit Credentials via HTTP**.
6. Observe the NetSecure packet analyzer extracting the HTTP POST body:
   ```http
   POST /api/dummy/login HTTP/1.1
   Host: 192.168.1.20
   Content-Type: application/x-www-form-urlencoded
   Content-Length: 64

   username=student_alex&password=Secr3tLabP@ssw0rd!&login_submit=true
   ```
7. Verify that Wireshark on Machine B would observe the exact same cleartext string in the TCP stream packet bytes!
8. Now switch to **HTTPS (Encrypted)** and submit again.
9. Verify that the packet bytes show only pseudorandom ciphertext:
   ```
   17 03 03 00 50 aa bb cc dd 12 34 56 78 ... [Encrypted TLS 1.3 Record]
   ```
   Demonstrating why HTTPS is mandatory for authentication security.

## 6. Viva Questions & Model Answers

**Q1: Why does Wireshark capture both ARP and ICMP when you ping an IP address for the first time?**  
*Answer:* Before Machine A can construct an Ethernet frame to send an ICMP Echo Request, it needs Machine B's Layer 2 MAC address. Machine A checks its ARP cache; if empty, it must first broadcast an ARP Request (`Who has 192.168.1.20?`). Once Machine B replies with its MAC address, Machine A caches it and dispatches the ICMP Echo Request.

**Q2: How does Machine A match an ICMP Echo Reply with its corresponding Echo Request?**  
*Answer:* In the ICMP header (RFC 792), both Echo Request and Echo Reply packets contain an `Identifier` (usually process PID) and a `Sequence Number`. When Machine B generates the reply, it echoes back the exact same Identifier and Sequence Number.

**Q3: Can an attacker sniff passwords on a switched Ethernet network as easily as on a Wi-Fi or Hub network?**  
*Answer:* In a standard switched network, switches forward unicast frames only to the designated port. However, attackers can still sniff traffic using **ARP Cache Poisoning (ARP Spoofing)** or MAC flooding, which tricks the switch into routing frames through the attacker's machine. Furthermore, on HTTP, any device along the transit route (gateways, routers, proxies) can read all data in plaintext.

**Q4: What cryptographic mechanism makes HTTPS resistant to passive packet sniffing?**  
*Answer:* HTTPS wraps HTTP in TLS (Transport Layer Security, RFC 8446). During the initial TLS handshake, the client and server use asymmetric cryptography (ECDHE) to securely agree upon ephemeral symmetric keys. All subsequent application data is encrypted with AEAD (Authenticated Encryption with Associated Data, such as AES-256-GCM or ChaCha20-Poly1305), ensuring complete confidentiality and tamper detection on the wire.
